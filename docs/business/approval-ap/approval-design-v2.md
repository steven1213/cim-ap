# 审批流系统落地方案 v2（对齐 cim-ap 现状）

> 基于原《审批流系统设计方案》修订。相对原稿的核心变更：**Flowable 8 + Boot 4 → 独立服务 + Flowable 7.2（与 cim-ap 同代）**；补齐**安全、回退/加签落地、合规审计**三块原稿缺口；明确**与 RMS 现有配方签核的衔接方式**。
>
> 决策记录（2026-10-14）：
>
> - 部署形态 = 独立微服务（不走 Boot 4 升级、不嵌入 cim-ap）。
> - 与 RMS 关系 = 平台做通用编排层，RMS 配方签核作为第一个业务方经 businessKey + 回调接入。
> - 第一步 = 仅产出本方档，不写实现代码。

---

## 0. 修订背景

原稿选型 Flowable 8.x（Spring Boot 4 / Spring Framework 7 / Jackson 3）已核实为**真实存在**（Flowable 8.0.0 于 2026-02-27 发布，官方支持 Boot 4；Spring Boot 4.0 GA 为 2025-11-20）。但其强制 Boot 4 / Hibernate 7 / Jakarta EE 11，**与 cim-ap 平台现栈（Spring Boot 3.3.5 / Hibernate 6.3.1 / JDK 21）无法同 JVM 共存**。若采用"嵌入 SDK"方案，须先把整个 cim-ap 升级到 Boot 4，波及所有模块、Flyway 序列、持久化单元扫描，风险与工作量过高。

故采用**独立微服务 + Flowable 7.2（Boot 3.3 同代、OSS 最稳）**，既保留原稿"双形态+回调解耦"的架构优点，又规避平台级升级风险。若未来确需 Flowable 8 新特性，可单独升级该服务，不影响 cim-ap。

---

## 1. 定位与边界

- **通用审批中台**：独立部署的微服务，拥有独立数据库（Flowable `ACT_`/`FLW_` 表 + 业务扩展表）。
- **不绑定具体用户体系**：鉴权复用 cim-ap **IAM（JWT RS256 + JWKS）**；组织/人员读取 IAM 组织树，不维护独立用户表。
- **业务方接入范式**：业务系统经 `businessKey` 发起流程、注册回调地址；审批结果由回调可靠回写，双方零流程知识耦合。
- **首个业务方 = RMS 配方签核**：经回调驱动现有 DRAFT→PENDING_SIGN→ACTIVE 语义与 eSignHash 证据链。

---

## 2. 技术栈定稿

| 维度   | 选择                                                                       | 理由                                                      |
| ---- | ------------------------------------------------------------------------ | ------------------------------------------------------- |
| 流程引擎 | **Flowable 7.2**                                                         | 与 cim-ap 同代（Boot 3.3），OSS 成熟、资料多；放弃 Flowable 8 新特性以换稳定性 |
| 应用框架 | Spring Boot 3.3.x                                                        | 与 cim-ap 一致，降低运维/排障成本                                   |
| 持久化  | Hibernate 6 / JDK 21                                                     | 与平台同代；独立库，前缀 `ACT_`/`FLW_` 不与 cim-ap `rms_` 冲突          |
| 集成方式 | **REST API + Java SDK client**（非 Boot Starter 嵌入）                        | 独立 JVM，避免版本耦合；业务方引 client jar 调 REST                    |
| 前端栈  | React + Vite + TypeScript（对齐 cim-ap Web）；UI 库待定（antd 6 生产就绪状态需确认，可先 5.x） | 复用 cim-ap 的 CSS 变量令牌体系，保证视觉一致                           |
| 实时推送 | SSE 为主、HTTP 轮询降级                                                         | 审批通知单向推送场景成熟，浏览器兼容好                                     |
| 可靠投递 | DB Outbox + 指数退避重试 + 死信告警                                                | 不引入额外消息中间件即可保证最终一致                                      |

## 3. 分层架构（沿用原稿四层，补边界）

```
[业务系统A] ──REST/SDK──┐
[RMS 配方签核] ──REST──┤──→ [审批流服务] ──→ [Flowable 7.2 引擎]
[IAM 组织树] ──REST──┤         │
                     │         ├── 回调服务（HMAC 签名 + 重试 + 死信）
                     │         ├── 消息通知（SSE + 多渠道）
                     │         └── 合规审计（append-only + 哈希链）
[前端 SPA] ──REST──┘
```

- **引擎核心层**：Flowable 7.2 承载 BPMN 2.0 定义、实例、任务流转；对外暴露统一 REST + Java SDK client。
- **业务集成层**：REST API（独立部署）供外部调用；SDK client jar 供业务方引入，封装发起/查询/执行动作。
- **消息通知层**：SSE 实时推送 + 多渠道触达（邮件/企微等）；审批任务事件经 `TaskListener`/`ApplicationEventPublisher` 入内部总线，由通知服务分发。
- **前端交互层**：流程设计器（bpmn.js / Flowgram.ai）+ 审批工作台 + 动态表单渲染。

**与 cim-ap 边界**：审批服务只调用 IAM 校验令牌与读取组织，不写用户数据；不引入 cim-ap 的 `cim-system` 权限表，自身维护"流程定义→权限码"映射。

---

## 4. 与 IAM / 组织的衔接（补原稿 IdentityService 抽象缺口）

- **鉴权**：业务方/前端调用审批服务须带 IAM 颁发的 JWT（RS256 + JWKS）；审批服务缓存并校验 JWKS，拒绝无效令牌。服务间回调采用**共享密钥 HMAC 或 mTLS**。
- **组织/人员**：审批选人、部门主管、角色成员均代理查询 IAM 组织树，审批服务**不落地用户表**。
- **免登直达**：原稿"免登链接"改为签发**短期（≤15min）签名令牌**（绑定 userId + taskId），过期/篡改即失效，杜绝越权入口。

---

## 5. 中国式审批落地细节（补原稿 R4 缺口）

### 5.1 会签 / 或签 / 串行 / 随机

多实例 `multiInstanceLoopCharacteristics`：

| 模式       | 完成条件（已补除零保护）                                                          |
| -------- | --------------------------------------------------------------------- |
| 按比例（过半）  | `${nrOfCompletedInstances >= Math.ceil(nrOfInstances * 0.5)}`（避免浮点除零） |
| 或签（一人即可） | `${nrOfCompletedInstances >= 1}`                                      |
| 依次审批     | `sequential=true`                                                     |
| 随机一人     | 候选随机分配单实例任务                                                           |

> 原稿 `${nrOfCompletedInstances/nrOfInstances >= 0.5}` 在 `nrOfInstances=0` 时除零，必须改为上方整数比较。

### 5.2 回退（jump back）

- Flowable 7 通过 `ManagementService.executeCommand(new ProcessInstanceJumpCmd(...))` 或自定义 `JumpCmd` 跳回任意历史节点。
- 回退动作须记录**跳转动因 + 操作人 + 时间戳**到审计（见 §8），禁止静默跳转。

### 5.3 前 / 后加签

- 运行时通过动态注入活动节点实现：前加签在当前任务前插入、后加签追加其后；当前待办按策略暂挂/续推。
- 加签人来源支持 IAM 组织查询（部门主管、角色、指定人）。

### 5.4 动态选人

- 任务创建时由"选人策略"解析（角色 / 部门主管 / 指定人 / 发起人自选），结果写回任务候选组/人；支持运行时改派，改派同样入审计。

## 6. 安全设计（补原稿 R3 缺口）

- **回调防伪造**：回调请求 HMAC-SHA256 签名（`timestamp + body + secret`），服务端验签并校验 timestamp 窗口（防重放）。回调地址注册需鉴权。
- **服务间通信**：mTLS 或共享密钥；审批平台不信任未签名请求。
- **免登链接**：如 §4，短期签名令牌代替永久链接。
- **租户隔离**：跨租户查询强制注入 `tenantId` 过滤，防止横向越权读取他方流程。

---

## 7. 回调与可靠投递（细化原稿 4.x）

- **注册模型**：回调注册表（`appCode → 回调 base URL + 密钥 + 激活状态`）。RMS 接入时在平台注册（如 `appCode=rms-ap`）。
- **投递流程**：业务事务内写 **DB Outbox 待投记录** → 调度器扫描 → 指数退避重试（最大 N 次）→ 死信 + 告警。
- **幂等**：每回调携带 `messageId`，业务方按 `messageId` 去重，避免重复回写。
- **对账**：开放"查询审批结果 / 回调状态"接口，业务方可对账或主动拉取。
- **回写语义**：平台只传结果（通过/驳回/各节点意见/完成时间）；业务方（RMS）更新自身状态并返回 2xx 确认；非 2xx 视为失败进入重试。

---

## 8. 合规审计（补原稿 R5 缺口）

- **不可篡改审计**：所有审批动作（提交 / 通过 / 驳回 / 回退 / 加签 / 改派 / 动态选人）记录操作人 + 时间戳 + 前后态，**append-only + 顺序哈希链**（沿用 RMS `eSignHash` 思路）。
- **与 RMS 衔接**：配方审批的证据链在 RMS 侧保留（`eSignHash` 证据链），审批平台审计作为中台级留痕，两者互补，满足半导体制造可追溯要求（ISO 9001 / 21 CFR Part 11 思路）。

---

## 9. 与 RMS 配方签核的衔接（核心）

**现状**（`RecipeSignoffService`，已落地）：状态机 `DRAFT→PENDING_SIGN→ACTIVE`、SignRoute 三路由、`eSignHash` 证据链、`body hash` 比对、批准自动激活、`batchDecision` 部分成功。

**目标衔接方式**：

1. RMS 发起配方签核时，向审批平台发起流程实例，`businessKey = recipeVersionId`，传入 SignRoute 路由信息。
2. 审批平台按会签/或签配置编排多人审批（原 RMS 单/多签语义上移到平台）。
3. 审批完成（或到达指定节点）触发**回调 RMS**。
4. RMS 在回调处理中**重放原有业务语义**：`body hash` 比对、`eSignHash` 生成、批准自动激活、驳回回 `DRAFT`。
5. 平台负责流转与多人编排，RMS 保留 `SignRoute`/`eSignHash` 作为回调内的业务校验与证据链。

**过渡策略**：保留 RMS 内 `SignRoute`/`eSignHash` 逻辑于回调侧；先选 **RMS 单一配方类型**跑通端到端，再推广。

---

## 10. 多租户

- Flowable `tenantId` 贯穿流程定义 / 实例 / 任务 / 历史 / 作业表；查询自动注入租户过滤。
- 组织/用户映射表按租户隔离；IAM 组织树按租户维度提供。
- 回调注册表按 `appCode`（含租户维度）隔离。

## 12. 开放问题 / 待确认

1. **前端 UI 库**：antd 6 是否生产就绪？建议对齐 cim-ap Web 现有栈（React + Vite + TS）。
2. **通知渠道**：审批平台自带轻量通知，重大事件是否桥接 IAM/企微？是否复用 RMS `NotifyChannel` SPI 思路（独立实现，不跨库）。
3. **部署归属**：独立服务是否纳入 cim 现有编排（docker-compose / K8s）与监控体系。
4. **流程定义存储**：BPMN 文件存库（Flowable 自带 `ACT_RE_*`）即可，是否需要额外的"流程模板市场"层由业务方自助配置。
5. **版本共存回归**：确认运行中实例按启动版本执行、新发起走最新版，需配套回归用例。
