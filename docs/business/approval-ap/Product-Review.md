# approval-ap 产品全方位体检报告

> 2026-10-15 基于代码实查（非凭空推测）+ 功能全景（Feature-Roadmap.md）+ 三条用户动线逐环节走查。
> 结论分级：🔴 阻断级（上线前必须修）/ 🟠 功能欠缺 / 🟡 缺陷与技术债 / 💡 动线优化。

---

## 一、总评

系统骨架完整度较高：五域功能（发起/审批/跟踪/配置/治理）齐备，P0/P1 动线闭环已落地，回调可靠投递、审计哈希链、formSchema 契约等设计超出同类最小可用产品水平。

但**当前形态是「内测可用、生产不可用」**：阻断项集中在**权限模型**——几乎全部接口的身份来自前端明文传参（query/body 的 `userId`/`actor`），且任务办理、附件操作完全不做授权校验。任何知道 taskId/attachmentId 的人都能代批、删证。这不是优化项，是上线闸门。

---

## 二、🔴 阻断级缺陷（必须修，已逐一实查确认）

| # | 问题 | 证据 | 影响 |
|---|------|------|------|
| 1 | **任务办理无办理人校验** | `completeTask` 只查任务存在（ApprovalProcessService:359-377），不比对 `req.actor()` 与 assignee/candidate；`return/addSign/reassign` 同样裸奔 | 任何用户可替任何人审批、回退、改派。审计链记录的是伪造身份 |
| 2 | **附件下载/删除零权限** | `GET /attachments/{id}/download` 无任何校验（AttachmentController:45-55）；`DELETE ?actor=` 只信传入参数 | 无关人员可下载敏感附件、可删除证据（虽有审计但删除者身份可伪造） |
| 3 | **身份体系未接入 JWT** | 全部端点 `userId/actor` 走 query/body 明文；dev 身份切换器直连 store | 上述两条的放大器。上线必须接 cim auth-starter（RS256+JWKS），身份从令牌取，前端传参一律忽略 |
| 4 | **孤儿实例风险** | Flowable 命令与 JPA 审计非同一事务；审计提交失败时流程已推进但审计缺失 | 审计哈希链断裂=合规承诺失效；详情权限判定（依赖 audit∪assignee）可能误拒。需 Flowable 命令后审计失败补偿或改为同事务资源 |

**修复顺序建议**：3 → 1 → 2 → 4（接了 JWT，1/2 的身份源即真实，补授权校验是小改动；4 需要事务设计）。

## 三、🟠 功能欠缺（按使用者分组）

### 发起人视角
- **详情内无催办/撤回入口**：目前只在「我发起的」列表行上。用户打开详情发现卡住 → 必须关弹窗回列表再操作，多一步断点
- **催办无频控**：可无限连点轰炸审批人（仅 SSE，无冷却/次数上限/记录聚合）
- **草稿单槽位**：`approval.draft.v1` 一个 key，A 定义填一半换 B 定义发起，草稿字段串台。应按 processKey 分槽
- 发起后无「预计审批路径」可视化——用户不知道会经过谁

### 审批人视角（最大缺口区）
- **详情内不能直接审批**（实查确认 DetailModal 无 approve/reject）：审批的核心场景是「点开详情 → 看表单/附件 → 决定通过或驳回」，现在必须看完关弹窗、回列表、点按钮。**这是全产品最刺眼的动线断裂**
- 无**批量审批**：30 条同类低风险单据要逐条点 30 次
- 无**委托代理**（P1 已列）：休假期间无人接管，只能改派逐条处理
- 待办无**排序/分组**选项（按紧急度/发起人/定义）
- 加签/回退的**目标人选无组织树/搜索**，纯手输用户名，输错静默失败或 404

### 管理员视角
- **定义无生命周期管理**：不能停用/下架旧版本（只能发起时过滤显示），旧 key 仍可经 API 发起
- **无实例运维能力**：管理员不能终止异常实例、转办僵尸任务（现只能进 Flowable 层面操作）
- **回调死信无主动告警**：DEAD 状态可查可手动重投（Callbacks 页），但没有人会天天去看——需要失败阈值告警（复用 notification 通道即可）
- **定义级租户隔离缺失**（已知决策遗留）：A 租户管理员能看到并使用 B 租户的模板

### 系统能力
- **统计报表缺失**（P1 剩余项）：平均处理时长、驳回率、各审批人负载——管理层角度这是审批系统的核心价值之一
- **通知渠道单一**：只有站内 SSE，关掉页面就收不到任何催办/超时/待办提醒。生产需要邮件/企业微信至少一条落地渠道（可作为回调通道的扩展）
- **抄送/知会**缺失（P2）：很多审批需要第三方知情但不参与

## 四、🟡 缺陷与技术债（已实查定位）

| # | 问题 | 位置 | 严重度 |
|---|------|------|--------|
| 1 | 列表全部无分页，`listTodo` 存在 **N+1 查询**（每任务单独查实例） | ApprovalProcessService:183-201 | 数据量增长后性能塌方 |
| 2 | 发起弹窗默认选中第一个定义（会签），会签需 `approvers` 列表、只填单人 assignee 直接 **500**——UI 应按所选定义动态渲染 approvers/assignee 字段而非让用户踩坑 | DefinitionsPage StartModal + 服务端缺参数校验（应 400 + 明确文案） | 高频踩坑 |
| 3 | `formData` 无服务端大小/结构限制：任意大 JSON 直接进流程变量表 | startProcess | 慢查询/存储膨胀风险 |
| 4 | `formSchema` 服务端不校验（key 重复、类型枚举外、order 冲突都静默接受） | 同上 | 低 |
| 5 | 超时扫描器内存 Set 去重：**重启后同任务重复推一次**；且每任务终身只推一次，任务持续超时再无提醒（应改为「每 N 小时重推」策略） | OverdueScanner | 低 |
| 6 | `BizException` 文案中文硬编码，前端 i18n 只覆盖自有文案，切英文后错误提示仍中文 | 全局 | 低 |
| 7 | H2（dev/测试）与 MySQL（生产）双迁移序列无 CI 一致性验证，字段类型漂移无守门 | db/migration | 中 |
| 8 | 审计 `detail` JSON 序列化失败时降级为明文拼接，哈希链覆盖的内容格式不统一 | completeTask:381-385 | 低 |
| 9 | 撤回无「已有审批票则不可撤」策略（决策记录在案，属已知取舍） | — | 需业务拍板 |

## 五、💡 动线走查结论

**发起人动线**：选模板 → 填单 → 提交 → 跟踪 → 催办/撤回
- ✅ 已闭环（formSchema 让审批内容可读、草稿暂存、撤回/催办/超时标红齐全）
- ⚠️ 两个断点：定义选择踩坑（缺陷#2）、详情内无操作入口

**审批人动线**：铃铛提醒 → 待办 → 看详情 → 决策
- ❌ **「看详情 → 决策」断裂**（第三节的头号问题）
- ⚠️ 回退/加签/改派的目标人选择无辅助

**管理员动线**：设计 → 部署 → 注册回调 → 监控
- ✅ 设计器结构校验较完备（出入边/分支语义/唯一开始结束）
- ⚠️ 校验缺「审批节点未配置办理人」警告——部署后运行到该节点任务成孤儿
- ⚠️ 回调监控被动，无死信告警

## 六、优先级建议（下一迭代排序）

| 优先级 | 事项 | 理由 |
|--------|------|------|
| P0（上线闸门） | 接 auth-starter JWT + 任务办理授权 + 附件权限 | 二、节 4 项 |
| P0 | 详情内嵌审批操作（通过/驳回/意见） | 最大动线断裂，改动小收益大 |
| P1 | 发起表单按定义类型动态渲染 + 服务端 400 校验 | 高频踩坑 |
| P1 | 列表分页 + N+1 消除 | 上线即会遇到 |
| P1 | 统计报表 + 通知落地渠道（邮件/企微） | 产品价值与触达 |
| P1 | 委托代理、批量审批 | 效率 |
| P2 | 定义生命周期管理、实例运维（终止/转办）、定义级租户隔离、死信告警、抄送 | 运营成熟度 |

---

## 七、一句话结论

**功能广度已经够用，当前瓶颈是「信任」与「顺手」**：信任 = 权限模型必须先于一切上线；顺手 = 审批人在详情里做决策、发起人在详情里催办，把最后两步断点接上。修完这两层，系统就具备了真实投放条件。
