# 审批系统需求文档（初稿 v0.1）

日期：2026-10-16　｜　状态：讨论稿，待评审　｜　来源：需求访谈（问答形式）

## 1. 项目概述

目标：建设一套企业内部使用的审批系统，支持拖拽式流程设计和中国式审批动作（加签、并签、催审等），既可独立部署，也可集成到已有系统。

定位与边界：

- 公司内部自用，单租户；不做多租户隔离与计费。
- 后端 Java / Spring Boot；流程引擎基于 Flowable 封装扩展（待国产库适配验证）。
- 规模按中等设计（500～5000 人，日均审批单数千），保留扩展空间。
- 终端：PC 网页为主；移动端 H5 仅做审批处理（同意、拒绝、加签、转办等），不做发起与设计。

设计方法：以用户操作动线设计业务流，按「角色 × 单据生命周期 × 业务场景」三个维度交叉推导功能（见第 5 章）。

## 2. 角色

| 角色 | 说明 |
| --- | --- |
| 发起人（申请人） | 单据业务归属人，条件分支与统计按其计算 |
| 代发起人 | 秘书/助理代领导发起，轨迹记录真实操作人 |
| 审批人 | 节点处理人，含加签人、转办接收人、代理人 |
| 办理人 | 办理节点处理人（如出纳），可回填字段 |
| 抄送人 | 只读知会 |
| 流程管理员 | 管理授权分类下的流程，可查看分类下所有单据，可干预在途单据 |
| 系统管理员 | 用户/部门/角色、接口应用、全局配置、审计 |

## 3. 总体架构与部署

系统分五层：用户端（PC、H5、嵌入组件、业务系统）→ 统一接入层（REST、MQ、Webhook，签名鉴权限流）→ 核心域 → 适配层 → 基础设施。

- 核心域八个模块：流程设计器、表单中心、审批引擎、任务与动作、组织与权限、通知中心、事件总线、审计与统计。
- 适配层四类：组织源、通知渠道、消息中间件、文件存储。

架构原则：

1. 依赖单向向下，核心域只依赖适配层接口，不依赖具体实现。
2. 一份核心代码，多种打包（独立服务、Starter、容器/K8s）。
3. 引擎封装：上层只认「流程 JSON 模型 + 命令」，不直接调用 Flowable API。
4. 状态变化统一走事件总线，事务发件箱保证事件不丢；无 MQ 时用数据库降级。
5. REST 与 MQ 指令共用同一层命令服务，均需鉴权与幂等。

部署形态：单机（一个 JAR + 一个数据库）；Docker / Compose（含可选 MinIO、文件预览服务）；Kubernetes Helm 多副本；Spring Boot Starter 嵌入宿主。多副本要求应用无状态、定时任务分布式去重；Starter 模式需表前缀隔离、可选独立数据源。

## 4. 功能需求

### 4.1 流程设计器（拖拽）

- 节点类型：审批、条件分支、并行分支、抄送、办理、子流程、自动节点（调用接口、定时等待、自动通过/拒绝）。
- 审批人指定：指定人、角色、部门主管、发起人自选等。
- 流程模型以 JSON 为业务标准，部署时转换为执行层模型。
- 节点字段权限：按「节点 × 字段」配置可见 / 可编辑 / 隐藏 / 必填。
- 节点级配置：超时规则、签署规则、退回策略。
- 发布前校验：无死路、审批人不为空、分支条件引用字段合法、被分支条件引用的字段不得在任何节点设为可编辑。

### 4.2 版本与发布

- 发布即生成不可变的新版本；在途单据永远按发起时的版本走完。
- 分级授权：按流程分类授权，流程管理员只能管理本分类。
- 发布需审批：流程变更本身走内置审批流。状态：草稿 / 待发布 / 已发布。

紧急修复：流程版本不可变，已发起的单据不会随流程修改而变化；紧急情况下通过管理员干预（替换审批人、跳过节点、重新派发任务）补救。

### 4.3 表单

- 两种模式：内置表单设计器（字段、校验、明细表、字段级权限）；宿主系统表单（发起时传入流程变量与表单地址，审批详情中嵌入渲染）。
- 引擎统一为「流程变量 + 表单引用」，条件分支不区分表单来源。
- 敏感字段可标记，加密存储、展示脱敏。
- 提交后表单对发起人锁定；节点字段权限是例外；所有修改留痕，可查看修改前后对比。
- 禁止编辑参与后续分支判断的字段；确需修改的，通过退回重提重新计算路径。

### 4.4 发起

- 个人草稿箱（手动保存 + 自动保存，仅本人可见）；基于历史单据再次发起 / 复制。
- 代发起：区分申请人与实际操作人。
- 发起前校验：流程可配置同步校验接口，不通过则拦截并展示原因；接口超时/失败策略可配置（放行或拦截）。
- 流程中可设置自动节点做中途校验，不通过时自动驳回或退回。

### 4.5 审批动作

| 动作 | 规则 |
| --- | --- |
| 同意 / 拒绝 | 意见是否必填可配置 |
| 前加签 | 加签人先审，审完回到本人，由本人决定 |
| 后加签 | 本人先通过，再交给加签人继续审 |
| 并加签 | 加签人与本人同时审，互不阻塞 |
| 转办 | 任务移交他人，本人退出 |
| 退回 | 可退到上一节点、指定节点或发起人；退回后重新提交，整个流程从头重走，轮次递增，旧轮次记录保留 |
| 撤回 | 发起人在下一审批人处理前可收回 |
| 征询补料 | 审批人向发起人提问，任务暂停；回复或补充附件后回到该审批人，不重走流程；暂停期间不计超时 |
| 评论追加 | 发起人与审批人可随时追加评论和附件，不影响流程状态 |
| 审批代理 | 休假/出差期间待审任务自动转给代理人 |
| 撤销（已通过单据） | 发起人发起撤销申请，走撤销审批；通过后原单作废并回调业务系统 |
| 管理员干预 | 强制终止、替换审批人、跳过节点、重新派发、直接作废（必填原因，单独审计） |

单据终态与撤销：已通过的单据经撤销审批通过或管理员作废后，进入「已作废」终态，并回调业务系统（需幂等）。撤销可配置使用独立的撤销流程，也可复用原流程的审批链。

加签边界情况（建议默认，待确认）：

- 嵌套加签：加签人可以再加签，层数上限可配置，建议默认 3 层。
- 加签后撤回：发起人撤回时，主任务与加签任务一并取消。
- 加签人离职：按 4.8 规则转交交接人或上级。

### 4.6 多人签署与并行

- 签署规则：会签（全部通过，任一人拒绝即驳回）、或签（任一人通过即通过）、依次签。按比例签不在第一版范围，通过条件设计为可扩展的策略接口。
- 并行分支：任一分支被拒绝，整个流程立即终止，其他分支未处理的任务作废（状态为「已取消」，轨迹写明原因，并通知相关审批人）。
- 并行分支内的退回只允许退到发起人或并行段之前的节点。

会签与依次签的拒绝收尾：

- 任一人拒绝，该节点立即以「拒绝」结束；同节点其他人未处理的任务置为「已取消」，轨迹写明原因并通知，已表态的意见保留。
- 拒绝后的去向按节点配置：默认「驳回并终止流程」，可选「退回发起人」。
- 依次签中有人拒绝，后续审批人不再生成任务。
- 或签没有「拒绝即结束」，全部人都拒绝时节点结果才为「拒绝」。

### 4.7 催审与超时

手动催办（发起人或已审人）、自动超时提醒、超时自动处理（自动通过 / 驳回 / 转交上级）、催办升级（通知审批人上级或流程管理员）。催办需限频与合并。

### 4.8 审批人解析与异常

- 发起人即审批人：自动跳过或自动通过。
- 相邻或前后节点为同一审批人：自动去重。
- 解析不到人（如部门无主管）：按规则转上级或指定管理员，规则可配置。
- 审批人离职/停用：待审任务自动转交交接人或上级。

### 4.9 办理节点

- 结果为「已办理」或「无法办理」；无法办理必须填原因，并退回到指定节点或发起人。
- 支持回填字段（如付款流水号、办理时间），复用节点字段权限机制。
- 办理完成时回调业务系统。默认策略：办理结果先落库，回调异步重试，失败告警，不回滚办理结果。

### 4.10 单据可见性

相关人员（发起人、审批人含加签与转办人、抄送人）；发起人的直属上级/部门主管；管辖分类的流程管理员；通过显式分享授权的人员。

### 4.11 通知

- 事件：新待办（含被加签、转办、代理）、我发起的单据有进展、抄送、超时提醒与催办升级、系统异常告警（回调失败、审批人解析失败，发给管理员）。
- 结构：事件 → 模板 → 渠道三层，渠道可配置，支持合并与限频。

### 4.12 附件

类型、大小、数量限制（可按表单字段配置）；必填校验；在线预览（图片、PDF，Office 为可选组件）；存储可切换（本地、MinIO、云 OSS）；下载与预览须经权限校验，使用短期签名链接。

### 4.13 审计、统计与输出

完整的审批轨迹与操作审计；效率统计（耗时、瓶颈节点、超时率、各流程发起量）；单据导出与打印 PDF（含审批意见与签名）；按条件导出 Excel。

### 4.14 组织与权限

内置完整的用户、部门、角色管理，同时支持对接外部组织源（SSO、LDAP、企业微信、钉钉、飞书）；内置与外部来源统一抽象；汇报线关系需一并同步。

### 4.15 集成

- 组织与账号：SSO、组织同步、IM 内免登。
- 业务系统：REST 发起与查询；Webhook 与 MQ 事件回调；MQ 指令（发起、撤回、催办）。
- 前端嵌入：iframe、微前端、组件 SDK。
- 消息渠道：邮件、短信、IM 机器人。
- 消息中间件：Kafka、Pulsar 等可插拔；无 MQ 时用数据库降级，保证独立部署开箱即用。

消息中间件的用途：向业务系统推送审批事件（与 Webhook 并存）；业务系统通过 MQ 异步发起审批、下发指令；系统内部异步解耦（通知发送、回调重试、延迟与定时任务）；没有 MQ 时用数据库发件箱与定时调度降级。

## 5. 用户动线

| 阶段 | 发起人 | 审批人 | 抄送人 / 管理员 |
| --- | --- | --- | --- |
| 发起前 | 选流程、填表单、存草稿、复制再发起、代发起 | – | – |
| 提交 | 提交（同步校验）；系统解析审批人 | 收到待办通知 | – |
| 审批中 | 查进度、催办、撤回、补料回复 | 同意、拒绝、退回、加签、转办、征询；代理人代处理 | 抄送人查看；管理员干预 |
| 超时 | 收到提醒 | 被提醒，超时自动处理或升级 | 升级通知 |
| 被退回 | 修改后重新提交（新一轮） | – | – |
| 结束 | 收到结果、打印 | – | 回调业务系统；进入统计 |
| 已通过后 | 发起撤销申请 | 撤销审批 | 管理员可直接作废 |

场景走查：已用「请假」（条件分支、抄送、回调考勤）和「报销」（明细表、并行审批、财务补填、出纳办理）两个场景验证，并由此补充了撤销、发起前校验、征询补料、草稿与代发起、并行拒绝与退回、办理节点、附件七项需求。

## 6. 关键业务规则

| 编号 | 规则 |
| --- | --- |
| BR-01 | 流程版本不可变，在途单据按发起时版本走完 |
| BR-02 | 被分支条件引用的字段不得设为节点可编辑，发布时校验 |
| BR-03 | 并行分支任一拒绝，立即终止流程，其他分支未处理任务标记「已取消」 |
| BR-04 | 退回后重新提交从头重走，轮次递增，旧轮次记录保留 |
| BR-05 | 并行分支内的退回只能到发起人或并行段之前的节点 |
| BR-06 | 征询补料期间暂停该任务的超时计时 |
| BR-07 | 办理结果先落库，回调异步重试，失败告警，不回滚 |
| BR-08 | 回调与 MQ 指令带签名、时间戳和幂等键，重复消息不重复生效 |
| BR-09 | 管理员作废必须填原因，并写入单独的管理员操作审计 |
| BR-10 | 审计日志只追加，使用哈希链防篡改 |
| BR-11 | 附件访问经单据可见性校验，不暴露永久直链 |
| BR-12 | 代发起时分别记录申请人与实际操作人 |
| BR-13 | 会签中任一人拒绝，节点立即以「拒绝」结束，同节点未处理任务置为「已取消」；去向默认驳回并终止，可配置为退回发起人 |
| BR-14 | 已通过单据经撤销审批通过或管理员作废后进入「已作废」终态，并幂等回调业务系统 |

## 7. 非功能需求

- 安全：登录增强（密码策略、失败锁定、会话超时、可选 MFA）；接口使用 AppKey + 签名，支持 IP 白名单与限流，回调验签；敏感字段加密与脱敏；审计防篡改，管理员操作单独记录，数据留存期限与归档。
- 规模与性能：按中等规模设计；应用节点无状态；定时任务分布式去重；统计数据基于历史表离线汇总，不拖慢在线审批。具体性能指标待定。
- 信创：数据库需适配达梦、人大金仓等；业务表通过 ORM / MyBatis 抽象，不写存储过程，不依赖数据库特有的 JSON 类型与函数；国产操作系统/CPU、国产中间件、国产浏览器暂不做专门适配，保持兼容。
- 可部署性：支持单机、Docker / Compose、K8s、Starter 四种形态，见第 3 章。
