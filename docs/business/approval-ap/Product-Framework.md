### 2.2 退回业务流程（核心闭环路径，v1.2 新增独立成章）

> 引擎能力已存在（`ApprovalReturnService` 经 `ChangeActivityStateBuilder` 迁回历史节点 + 前端退回弹窗），缺的是产品语义。以下为完整产品定义。

#### 2.2.1 三态语义边界（打回路径）

| 维度        | 退回 (RETURN)                 | 驳回 (REJECT)          | 撤回 (WITHDRAW) |
| --------- | --------------------------- | -------------------- | ------------- |
| 触发者       | 审批人 / 办理人（无法办理时）            | 审批人                  | 发起人           |
| 流程结果      | **不终止，回环重走**                | 终止（D4）               | 终止            |
| 终态 result | —（中间态）                      | REJECTED             | WITHDRAWN     |
| 去向        | 上一节点 / 指定历史节点 / 发起人         | 业务方回退状态（RMS 回 DRAFT） | 业务方作废         |
| 重入方式      | 发起人修改后**重新提交**（轮次+1，§2.2.3） | 重新发起（新实例）            | 重新发起（新实例）     |
| 意见必填      | 是                           | 是（已实现）               | 否             |
| 流程版本      | 原定义（BR-01，重提不换版）            | —                    | —             |

#### 2.2.2 动作可用性矩阵（节点类型 × 角色）

| 动作      | 发起人                | 审批人 | 办理人            | 加签人 | 域管理员                       |
| ------- | ------------------ | --- | -------------- | --- | -------------------------- |
| 通过 / 驳回 | —                  | ✅   | —（结果为已办理/无法办理） | ✅   | —                          |
| 退回      | —（仅重新提交）           | ✅   | ✅（无法办理即退）      | ✅   | —                          |
| 前/后/并加签 | —                  | ✅   | —              | ✅   | —                          |
| 转办 / 改派 | —                  | ✅   | ✅              | ✅   | —                          |
| 撤回      | ✅（下一人处理前；加签任务一并取消） | —   | —              | —   | —                          |
| 催办      | ✅（含已审人）            | —   | —              | —   | —                          |
| 征询补料    | —                  | ✅   | —              | —   | —                          |
| 撤销已通过单据 | ✅（走撤销流程）           | —   | —              | —   | —                          |
| 管理员干预   | —                  | —   | —              | —   | ✅（强制终止/替换审批人/跳过节点/重新派发/作废） |

**退回目标限制**：

- 仅限**已审批过的历史活动节点**（不得跳入未走过的分支节点，防双令牌/并行段错乱）；
- 不含加签临时任务（加签为任务级挂件，非流程节点）；
- 并行段内节点：仅允许退到「发起人或并行段之前的节点」（BR-05）；
- 默认目标 = 上一节点；可选「发起人」「指定历史节点」。

#### 2.2.3 主流程（7 步）

1. **触发**：审批人在待办详情点「退回」→ 弹窗：目标节点（上一节点/发起人/指定历史节点下拉）+ 退回意见（必填）
2. **前端校验**：目标合法性（并行段限制/仅历史节点）+ 轮次未达上限（默认 5，`approval.return.max-rounds` 可配）
3. **后端执行**：当前任务关闭（结果 RETURNED）；**会签收尾**——同节点其他未处理任务取消并通知（对齐 BR-13 思路），已表态意见保留；execution 迁回目标节点
4. **系统动作**：轮次 `round+1`（流程变量 + 任务字段）；审计 RETURN 入哈希链（操作人/目标/原因/轮次）；发起人待办出现「**修改并重新提交**」任务
5. **通知**：企微推送发起人（审批人+意见+单号+「需修改后重新提交」）；被取消任务的处理人收「任务已取消」通知
6. **发起人修改**：我发起的 → 详情（「第 N 轮 · 已退回」徽标）→ 表单在**发起人节点字段权限**范围内解锁（被分支条件引用的字段仍禁编辑，BR-02）→ 修改 → 「重新提交」
7. **重新提交**：实例从开始节点重走，条件分支按新表单值重新评估；版本仍为原定义；旧轮次任务全部关闭；`RESUBMIT` 入审计；业务方收中间事件回调（若开启，F20）

#### 2.2.4 分支与异常（6 条）

| #  | 场景           | 规则                                                    |
| -- | ------------ | ----------------------------------------------------- |
| E1 | 会签中一人退       | 节点立即以「退回」结束；其他未处理任务取消+通知；已表态意见保留                      |
| E2 | 并行段内退        | 仅允许目标=发起人或并行段前节点（BR-05）；其他目标前端过滤+后端 400 双保险           |
| E3 | 轮次达上限        | 退回按钮禁用+提示「已达退回上限，请联系流程管理员」；管理员可干预（F4）或提升上限            |
| E4 | 退回待修改期间发起人撤回 | 允许（撤回优先）；重提入口关闭；回调 WITHDRAWN                          |
| E5 | 退回后长期不处理     | 「修改并重新提交」任务计超时（复用 OverdueScanner，阈值同全局）；超时通知只催不改（发起人） |
| E6 | 退回到的节点审批人已离职 | 按 F7 解析异常规则转交交接人或上级                                   |

#### 2.2.5 前端动线

- **审批人**：待办 → 详情 → 退回 → 弹窗（目标+必填意见）→ 确认
- **发起人**：我发起的（「第 N 轮」徽标）→ 详情 → 表单编辑 → 重新提交
- **已审人**：已办列表中同单再现时标注「第 2 次审批」，避免「这单我不是审过了吗」困惑

#### 2.2.6 审计与回调

- 审计：`RETURN`（操作人/目标/原因/轮次）、`RESUBMIT`（发起人/轮次/表单变更摘要）入哈希链
- 回调：`TASK_RETURNED` / `TASK_RESUBMITTED` 作为**中间事件**（默认关，按 appCode 可开，见 F20）

#### 2.2.7 验收标准（Given/When/Then）

- Given 会签节点 3 人待办，When 其中 1 人退回到发起人，Then 实例保持 RUNNING、`round=2`、其余 2 人任务取消且收到通知、发起人待办出现「修改并重新提交」
- Given 实例 round 已达上限，When 审批人点退回，Then 前端禁用且后端 400（双保险）
- Given 并行分支内节点，When 选择非允许目标，Then 前端过滤且后端 400
- Given 退回待修改中，When 发起人修改表单并重新提交，Then 实例从开始节点重走、条件按新值重评、版本=原定义、旧轮次任务全部关闭、审计记 RESUBMIT

### 切片3 落点（G1/G3/G9）
- **G9 开放 API 安全**：`ApiAuthFilter`（`@ConditionalOnProperty approval.api.security.enabled`）。仅对携带 `X-App-Key` 的服务间调用生效，不影响 JWT 用户态 / dev 放行。校验链：未知 appKey → 缺/错签名 → 时间戳超重放窗口（默认 5min）→ IP 白名单 → 按 appCode 限流（默认 60/min）→ 跨业务域；任一失败 403 + `[API-SEC-ALERT]` 告警（`WebhookNotifyService`）。签名 = `HMAC-SHA256(timestamp|method|path|body)`，常量时间比较。
- **G3 appCode 业务域隔离**：定义（部署时可选 `appCode` 作为 Flowable tenantId）/实例/任务/审计/回调五类查询按 appCode 收敛；跨域访问 **403**（不返回 404）；审计实体新增 `app_code` 列并落库（落点从流程实例变量 `tenantId` 解析）；`SecurityGuard.assertAppCodeScope` 统一拦截。
- **G1 权限码三层**：`SecurityGuard.assertPermission` 接 cim-system 平台码（`approval:definition:manage` / `approval:callback:manage` / `approval:audit:view` / `approval:instance:admin`）；认证态按 Spring Security 权威校验，**平台超管（`ROLE_SUPER_ADMIN`，由 IAM `is_super` 展开）跨域**；dev 态 `dev-bypass` 默认放行、`dev-enforce` 可开启 deny 路径（`dev-super-admin` 白名单）。管理端点 deploy/suspend/回调注册/审计查看已加守卫。
- **前端收敛**：业务域隔离经由既有 `tenantId` 切换器承载（待办/发起/详情均按 tenantId 收敛），本切片未引入新前端改动。
